# 旅行需求提取：三个职责边界

这一阶段只把用户的自然语言旅行描述变成可靠的 `TravelRequest`，并列出规划前仍需确认的信息。它不生成行程、不查询实时数据，也不把未知信息补成看似完整的计划。

## 模型：理解并提取已表达的信息

LangChain 的 Prompt 会要求模型只提取用户明确给出的目的地、日期、天数、人数、预算、偏好和限制。模型可以从“2026-11-10 出发、玩 3 天”这种确定组合得到结束日期，但不能因为“带父母”擅自填写三个人，不能补预算，也不能猜测日期。

模型的输出使用 `TravelRequestExtraction` 这个 Structured Output schema；其中没有 `missing_fields`，避免把业务流程判断交给模型。

## Pydantic：守住数据边界

`TravelRequestExtraction` 和最终的 `TravelRequest` 都由 Pydantic 校验。日期必须能解析为明确日期；天数和人数必须是大于零的整数；结束日期不能早于出发日期。空的偏好和限制各自使用独立列表，因此不同请求不会共享数据。

若模型返回 `days=0`、负人数或不合法日期，程序会拒绝整个结果，并明确说明结构化数据没有通过校验，不会返回一份貌似成功的旅行需求。

## 普通 Python：计算确定性的流程状态

模型提取和校验完成后，普通 Python 根据当前规则计算 `missing_fields`。规划前必须确认的字段依次是：`destination`、`start_date`、`days`、`traveler_count` 和 `budget`。`preferences` 与 `constraints` 允许为空。

同样，只有当出发日期和天数都已确定时，程序才计算结束日期（出发日算第 1 天）。这种确定性流程规则放在代码中，后续的追问流程可以直接使用，且不受模型对“是否缺信息”的判断影响。

## 本地运行

配置 `.env` 中的 `DATA_API_KEY` 和 `DATA_MODEL` 后，在仓库根目录运行：

```bash
python -m backend.travel_assistant "我和朋友两个人计划 2026 年 11 月 10 日去杭州玩 3 天，预算 5000 元。"
```

不带参数时会提示输入描述。空输入、缺少配置、模型调用失败和结构化校验失败都会返回清晰提示，且不显示 API Key、完整服务响应或模型推理内容。
